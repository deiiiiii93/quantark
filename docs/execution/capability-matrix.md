## Rationale notes

1. single-solve engine without a batch axis; introducing one is a changed numerical plan - re-scope on Phase 2 benchmark evidence (spec 21)
2. sequential run_rqmc mode exists but session adaptive planning is deferred with the single-solve batch scope (spec 21 re-scope on Phase 2 evidence)
3. no cross-request preparation artifacts; draw reuse is DrawRepository (Phase 2) and the batch/adaptive states cover execution
4. engine has no adaptive RQMC stopping mode
5. LSM regression couples all paths cross-sectionally; no independent batch decomposition exists
6. adaptive RQMC compatibility stopping is sequential by contract (spec 8.4); parallel-wave deferred on Phase 2 benchmark evidence (host-limited thread scaling)
7. Dupire local-vol surface served from the session artifact cache through prebuilt-surface clones (Phase 1)
8. abstract base class
9. PDE solve has no batch axis; Phase 4 covers PDE preparation and rich outcomes
10. grids, term-structure step coefficients, and factorization packs (and the Dupire surface where the model has one) behind PreparedArtifactCache descriptors; one value solve serves PV/event/grid outputs
11. frozen construction-owned model inputs; time-dependent ADI/kernel operators cannot prove factorization reuse safe and are rebuilt (spec 9.2 legality); no session artifacts
12. one-value-solve session rich outputs (PV + event stats) through a prepared clone; time-dependent ADI operators are rebuilt (spec 9.2 legality), so no factorization artifacts
13. engine-internal kernel discretization; preparation cost negligible; no session artifacts
14. not an MC engine; batch capability does not apply
15. facade dispatches per product type; prepared adapters bind at the solver level
16. FX MC engines are single-solve on the shared montecarlo layer; batch decomposition re-scoped on Phase 2 benchmark evidence
17. environment-bound engine builds internal grids per solve; no shareable artifacts (spec 9.2: rebuilt)

## Session-level capabilities

Scenario, process, and Dask execution are SESSION-level capabilities
(`PricingSession.run_scenarios` plus registered transformer/runner/factory
ids), not per-engine ones — any engine an adapter or runner can drive
participates. The inventory therefore carries no per-engine scenario column;
the scenario exit gates live in `test/execution/test_scenario_*`,
`test_worker_spec`, `test_processes_backend`, `test_dask_backend`, and
`test_surface_shock_scenarios`.
