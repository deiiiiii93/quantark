# 1D MC migration of the 2D perf program — measured decision matrix

**Date:** 2026-08-10.  **Branch:** `worktree-mc1d-perf-migration` (= `main`
+ two cherry-picks from the 2D program: `make_df_fn` dedup and the shared QE
kernel module).  **Question:** which of the six techniques introduced in the
2D (Heston/SLV) MC engines carry into the 1D engines, and at what measured
benefit?  Everything below is measured on this host (arm64, numba 0.66,
numpy 2.4.6) by the standalone runtime-patched demos in this directory.
**No engine code has been changed.**

## Where 1D time actually goes (`prof_baseline.py`)

| Run | Wall | Dominant cost |
|---|---|---|
| Euro MC pseudo 200k×252 | 0.72 s | path build (normals + exp + cumprod) ≈ 72% |
| Snowball MC 100k×252, continuous KI | 0.96 s | bridge-KI check 59%, path build 38% |
| LV euro kernel 100k×252 (25×61 grid) | 1.33 s | `local_vol` lookup **82%** (searchsorted 0.58 s) |
| LV barrier kernel 100k×252 | 2.05 s | `local_vol` 54% + bridge survival 22% |

Structural difference from 2D: all BSM 1D engines share one path core
(`GBMPathGenerator`), so one fix reaches ~14 products; the LV kernels and the
LV variants of the vol-model engines share `LocalVolSurface.local_vol`.

## Bitwise proof technique

Same as the 2D program: identical inputs through shipped vs candidate code,
`.tobytes()` / `float.hex()` equality asserted — not assumed — because NumPy
2.x SIMD transcendentals need not match scalar libm. On this host they match
exactly for both `exp` (candidate 2) and the interpolation chain (candidate 1),
replicating the 2D QE finding. `fastmath` stays off; candidate 2 multiplies
`s0` after the cumprod fold, never inside the accumulator, because FP
multiplication is not associative.

## Deliberately not done (recorded for the next round)

- **Numba fusion of the LV step loop** (lookup + exp update per step): after
  candidate 1, `searchsorted` over genuinely-distinct strikes remains the LV
  floor. A fused kernel is the 1D analogue of the 2D program's unfinished
  "fuse the rest of `simulate`" lever — a project of its own, with the same
  bitwise-risk profile. Unmeasured; do not start it without a profile of the
  post-candidate-1 state.
- **Numba for the bridge-KI loop**: rejected on RNG grounds, not effort —
  draws are `rng.random(idx.size)` with data-dependent sizes; numba cannot own
  a `Generator` stream bit-compatibly, and pre-drawing changes the stream
  (re-baseline territory; exact-semantics-by-default says no).
- **MultiAssetGBMPathGenerator tail**: same exp/cumprod shape as candidate 2;
  extend the kernel there once the single-asset version is accepted.
- **Normal generation** (0.19 s of the euro run): irreducible without changing
  the stream.

## Production validation: the otc-price-adapter full trade book — 2026-08-11

The synthetic benchmarks above measure kernels. This section measures a real
99-row desk book (`/Users/fuxinyao/otc-price-adapter`, as-of 2026-06-26:
75 snowballs, 13 phoenixes, 11 vanilla/digital/barrier/sharkfin), priced
through the adapter's own `price_row` with full Greeks, under the base tree
and the Phase-1 tree via `PYTHONPATH` shadowing. Both trees ran back-to-back
in one load window, serially, from a venv where numba IS installed.

### Why the gap, measured rather than guessed

`cProfile` of one heavy snowball row (`GJZQ-DCRX7-20260601-OPTION-01`,
~16 s, 7 pricings for base + Greek bumps) under Phase 1:

| tottime | share | where |
|---|---|---|
| 5.11 s | **32%** | `qmc_brownian_bridge.transform` |
| 4.66 s | **29%** | `qmc_sobol.normal` (Sobol + inverse-CDF) |
| 2.75 s | 17% | `gbm_kernels._kernel` ← **the part Phase 1 accelerated** |
| 1.25 s | 8% | `_check_ki_barriers` |
| 0.91 s | 6% | scipy `_qmc._random` |

The path build is only ~17% of a production autocallable pricing after
acceleration (~24% before), so Amdahl caps the achievable row gain near
1.10× — which is what the book delivered. The European microbenchmark showed
1.61× because there the path build is ~72% of the run. **Both numbers are
correct; they measure different workloads.** Quote the 1.06× for desk
throughput and the 1.61× only for path-generation-bound work.

Note also that this book never exercises candidate 1: the adapter prices with
BSM engines on flat/market vol, never `LocalVolSurface`. C1's 1.68× applies to
LV/SLV workflows (e.g. the snowball vol-model backtest), not to this book.

### The lever this exposes: the QMC draw pipeline

Bridge + Sobol are **61%** of an autocallable MC row — 3.6× the share of what
Phase 1 optimized. `BrownianBridge.transform` (`qmc_brownian_bridge.py:105`)
is a Python loop over ~400–500 steps whose body reads and writes *columns*
(`W[:, l]`, `W[:, r]`, `W[:, k]`) of a C-contiguous `(n_paths, n_steps)`
array — stride `n_steps × 8` bytes per element, the cache-hostile access
pattern the fused kernel already fixed for the path build. A per-path fused
Numba kernel carrying the bridge recursion in registers is the same
transformation, with the same bitwise argument available (the recursion is
sequential per path and order-preserving).

Estimated payoff if the bridge alone reached 3×: ~1.27× per autocallable row,
i.e. larger than everything Phase 1 delivered on this workload. **Unmeasured —
this is a spike candidate, not a promise.** It belongs in the WS-3 slot the
fused-scan spike vacated.

### METHODOLOGY TRAP: cross-window timing comparisons are worthless here

The first bridge measurement came out at **1.73×** and was wrong. This is a
shared machine, and another session's ~340%-CPU job finished between the
base run and the bridge run. Re-running the **unchanged base tree** in the
new window gave 1186.4 s → 918.0 s: **the baseline "sped up" 1.29× with no
code change at all.** The 1.73× was that load artifact multiplied by the
real gain.

Rule for this repo's perf work, learned the expensive way: **both arms of any
timing claim must run back-to-back in one window, and if hours pass, re-run
the baseline too.** Correctness comparisons (byte equality) are immune to
this; only timings are affected. Check `ps`/`uptime` for competing load
before trusting a headline ratio.

## Brownian-bridge kernel spike — 2026-08-11: PASSED ITS GATE, ready to wire

`demo_bridge_kernel.py`. Chosen because the adapter book put
`BrownianBridge.transform` at 32% of a production autocallable row (vs 17%
for the path build Phase 1 accelerated). Gate declared before measuring:
byte-identical `dW` AND ≥2.0× on the transform at production shape.

| Check | Result |
|---|---|
| Bitwise sweep (7 uniform grids, non-uniform, clustered × 3 path counts, plus an all-zero sign-of-zero trap) | **36/36 IDENTICAL** |
| Transform 100k × 252 | 207.3 → 103.3 ms = **2.01×** |
| Transform 100k × 488 (production shape) | 433.6 → 197.8 ms = **2.19×** |
| Transform 8192 × 252 (small) | 9.5 → 7.3 ms = 1.30× |
| End-to-end snowball QMC 100k × 488 | 0.718 → 0.608 s = **1.18×**, price bit-equal |
| **Gate (bitwise AND ≥2.0×)** | **PASS** |

The 1.18× end-to-end matches the ~1.19× Amdahl predicted from a 32% share at
2.2×, which is the cross-check that the microbenchmark is not lying.

**Why it works:** the shipped loop walks steps in Python and reads/writes
*columns* of a C-contiguous `(n_paths, n_steps)` array, so each vector op
strides `n_steps × 8` bytes per element. The kernel walks one path at a time
with the recursion in registers and row-major access. Gains grow with
`n_steps` (1.30× at 252 small-path, 2.19× at 488) exactly as a
stride-dominated cost predicts.

**Two order traps respected, both load-bearing for bitwise:**
1. `mean` keeps the shipped grouping `(a*W_l + b*W_r) / denom`. Folding
   `a/denom` into a coefficient reassociates and is NOT bitwise.
2. When `left == -1` the shipped code still evaluates `a*0.0` and adds it.
   Skipping that term flips the sign of a zero (`0.0 + -0.0 == +0.0` while
   `-0.0` alone stays `-0.0`) — invisible to `allclose`, caught by a byte
   compare. The all-zero-normals case in the sweep exists to pin this.

Unlike the path kernel, the bitwise claim here rests on firmer ground: every
operation (`+ - * /` and `sqrt`) is IEEE-754 correctly rounded, so a scalar
loop and a SIMD vector op must agree. No empirical libm-vs-SIMD question.

## Free win found while spiking: the QMC path count is a power-of-two cliff

`SobolNormalGenerator.normal` generates `_next_power_of_two(n_paths)` points
to preserve Sobol balance, then slices. Measured at dim=488:

| Requested | Generated | Discarded | Time |
|---|---|---|---|
| 65,536 | 65,536 | 0 | 281.4 ms |
| **100,000** (the desk's `pathNumMC`) | **131,072** | **31,072 (23.7%)** | **560.4 ms** |
| 131,072 | 131,072 | 0 | 566.7 ms |

**The desk pays for 131,072 paths and uses 100,000.** Setting `pathNumMC` to
131,072 buys 31% more paths for 1.1% more time; setting it to 65,536 halves
the Sobol+ndtri cost. This is a config change in the adapter, not a code
change here, and it is a bigger lever on the Sobol 29% than any rewrite —
`normal()` itself is already in-place and vectorized with no Python-level
waste, so a numba rewrite would mean reimplementing scipy's Sobol direction
numbers and `ndtri`: high effort, high risk, unlikely to win. **Recommend the
config change; do not rewrite Sobol.**

## WS-3 fused path+scan spike — 2026-08-10: FAILED THE GATE, not wired

`demo_fused_snowball_kernel.py`. A Numba kernel that builds each path and
scans discrete KO/KI observations in one pass, never materializing the
`(n_paths, n_steps)` path matrix. Gate was bit-identical primitives AND
≥1.5× on the stage.

| Check | Result |
|---|---|
| `first_ko`, `ki_trig`, `first_ki`, `terminal`, standard + reverse | all IDENTICAL |
| Stage speedup (100k × 252, best of 5) | 215.3 ms → 182.8 ms = **1.18×** |
| Gate (bitwise AND ≥1.5×) | **FAIL** |

**Why it under-delivered, and why that is informative.** The baseline here is
the *post-Phase-1* pipeline, whose path build is already the fused Numba
kernel. Everything the single-pass design has left to save is the ~200 MB
path-matrix write plus the scan's gathers — worth 18% of the stage, and the
stage is only part of a pricing, so end-to-end this would land in the
single-digit percents. That does not justify a second code path through the
engine with its own bitwise surface.

**Not a dead end, a re-ordering.** The fusion idea is only cheap *because*
Phase 1 already banked the path-build win; the two are substitutes, not
complements. Revisit only if a future workload is dominated by scans over
many barriers (e.g. multi-barrier phoenix ladders on long grids), where the
gather side grows while the path build does not.
