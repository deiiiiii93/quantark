# 1D MC migration of the 2D perf program — measured decision matrix

**Date:** 2026-08-10.  **Branch:** `worktree-mc1d-perf-migration` (= `main`
+ two cherry-picks from the 2D program: `make_df_fn` dedup and the shared QE
kernel module).  **Question:** which of the six techniques introduced in the
2D (Heston/SLV) MC engines carry into the 1D engines, and at what measured
benefit?  Everything below is measured on this host (arm64, numba 0.66,
numpy 2.4.6) by the standalone runtime-patched demos in this directory.
**No engine code has been changed.**

## Where 1D time actually goes (`prof_baseline.py`)

| Run | Wall | Dominant cost |
|---|---|---|
| Euro MC pseudo 200k×252 | 0.72 s | path build (normals + exp + cumprod) ≈ 72% |
| Snowball MC 100k×252, continuous KI | 0.96 s | bridge-KI check 59%, path build 38% |
| LV euro kernel 100k×252 (25×61 grid) | 1.33 s | `local_vol` lookup **82%** (searchsorted 0.58 s) |
| LV barrier kernel 100k×252 | 2.05 s | `local_vol` 54% + bridge survival 22% |

Structural difference from 2D: all BSM 1D engines share one path core
(`GBMPathGenerator`), so one fix reaches ~14 products; the LV kernels and the
LV variants of the vol-model engines share `LocalVolSurface.local_vol`.

## Bitwise proof technique

Same as the 2D program: identical inputs through shipped vs candidate code,
`.tobytes()` / `float.hex()` equality asserted — not assumed — because NumPy
2.x SIMD transcendentals need not match scalar libm. On this host they match
exactly for both `exp` (candidate 2) and the interpolation chain (candidate 1),
replicating the 2D QE finding. `fastmath` stays off; candidate 2 multiplies
`s0` after the cumprod fold, never inside the accumulator, because FP
multiplication is not associative.

## Deliberately not done (recorded for the next round)

- **Numba fusion of the LV step loop** (lookup + exp update per step): after
  candidate 1, `searchsorted` over genuinely-distinct strikes remains the LV
  floor. A fused kernel is the 1D analogue of the 2D program's unfinished
  "fuse the rest of `simulate`" lever — a project of its own, with the same
  bitwise-risk profile. Unmeasured; do not start it without a profile of the
  post-candidate-1 state.
- **Numba for the bridge-KI loop**: rejected on RNG grounds, not effort —
  draws are `rng.random(idx.size)` with data-dependent sizes; numba cannot own
  a `Generator` stream bit-compatibly, and pre-drawing changes the stream
  (re-baseline territory; exact-semantics-by-default says no).
- **MultiAssetGBMPathGenerator tail**: same exp/cumprod shape as candidate 2;
  extend the kernel there once the single-asset version is accepted.
- **Normal generation** (0.19 s of the euro run): irreducible without changing
  the stream.

## Phase-1 landing — 2026-08-10

Candidates 1 and 2 landed as `81b1ac2` (LV scalar-t fast path) and
`1dc509c` + `f28f654` (shared GBM kernel + generator wiring), per
`docs/superpowers/plans/2026-08-10-mc1d-perf-phase1.md`.

**Detached-worktree byte gate (spec §2.1).** `probe_phase1.py` run against a
detached worktree at `mc1d-phase1-base` (`b38dd3d`) and at the landed branch,
`gbm_backend()` = `numba` on the new tree:

| Dump | Bytes | Result |
|---|---|---|
| `paths_pseudo.bin` (4096 × 127 GBM paths) | 4,161,536 | IDENTICAL |
| `paths_sobol.bin` (Sobol + Brownian bridge) | 4,161,536 | IDENTICAL |
| `euro.bin` (EuropeanMCEngine 100k × 252) | 8 | IDENTICAL |
| `lv.bin` (LV euro + LV barrier prices) | 16 | IDENTICAL |

**8,323,096 bytes byte-identical.** No golden re-freeze required.

**End-to-end speedups**, both trees timed back-to-back in one machine-load
window (best of 3 each), which is the fair comparison — standalone demo
numbers taken hours apart drift with load:

| Path | Base (`b38dd3d`) | Phase 1 | Gain | Candidate exercised |
|---|---|---|---|---|
| EuropeanMCEngine 100k × 252 pseudo | 0.518 s | **0.321 s** | **1.61×** | C2 only (GBM kernel) |
| LV European kernel 50k × 252 (25×61 grid) | 0.866 s | **0.514 s** | **1.68×** | C1 only (LV lookup) |

**The two probes isolate one candidate each — they do not compose.** The LV
kernels run their own RNG loop and never touch `GBMPathGenerator`, and
`EuropeanMCEngine` never touches `LocalVolSurface`. Both figures exceed the
demo-stage estimates (1.33× / 1.46×), which were measured at different path
counts with both arms sharing one process; the two-tree probe (clean
processes, one load window) is the authoritative measurement and the demo
estimates were conservative.

Products that DO exercise both — the LV/SLV snowball vol engines, which build
paths through the shared generator and sample a `LocalVolSurface` per step —
are not measured here; their combined gain is expected to exceed either
figure but remains unmeasured.

## WS-3 fused path+scan spike — 2026-08-10: FAILED THE GATE, not wired

`demo_fused_snowball_kernel.py`. A Numba kernel that builds each path and
scans discrete KO/KI observations in one pass, never materializing the
`(n_paths, n_steps)` path matrix. Gate was bit-identical primitives AND
≥1.5× on the stage.

| Check | Result |
|---|---|
| `first_ko`, `ki_trig`, `first_ki`, `terminal`, standard + reverse | all IDENTICAL |
| Stage speedup (100k × 252, best of 5) | 215.3 ms → 182.8 ms = **1.18×** |
| Gate (bitwise AND ≥1.5×) | **FAIL** |

**Why it under-delivered, and why that is informative.** The baseline here is
the *post-Phase-1* pipeline, whose path build is already the fused Numba
kernel. Everything the single-pass design has left to save is the ~200 MB
path-matrix write plus the scan's gathers — worth 18% of the stage, and the
stage is only part of a pricing, so end-to-end this would land in the
single-digit percents. That does not justify a second code path through the
engine with its own bitwise surface.

**Not a dead end, a re-ordering.** The fusion idea is only cheap *because*
Phase 1 already banked the path-build win; the two are substitutes, not
complements. Revisit only if a future workload is dominated by scans over
many barriers (e.g. multi-barrier phoenix ladders on long grids), where the
gather side grows while the path build does not.
